# 越权 / IDOR playbook

## 先画角色矩阵

| 响应 | 含义 |
|---|---|
| 302 → /login | 未登录 |
| 403 | 已登录，角色不对 |
| 404 | 资源不存在或按归属隐藏 |
| 200 | 可访问（需看内容是否属于该角色） |

三个工作台（buyer/merchant/admin）要分别登录，使用**不同 cookie jar**。不要用管理员会话测“未授权”。

## 测试设计

1. **垂直越权**：低角色访问高角色路由（`/admin/*`、`/merchant/*`）。
2. **水平越权/IDOR**：同角色访问他人对象（订单、发票、工单、地址、文件）。
3. **跨租户**：商户 A 访问商户 B 的订单/商品/报表。
4. **参数篡改**：`user_id`、`merchant_id`、`role`、`owner_id`、`tenant_id`。
5. **批量赋值**：注册/资料更新塞 `role=admin`、`is_admin=1`、`supplier_id=1`。
6. **状态机**：取消/退款/发货越权，或跳过步骤。

## 判定

- 配置 deny 的角色返回 200 且页面不是登录/403/404 → 越权。
- 同一对象两个角色都 200 且内容高度相似 → 共享对象（需人工确认字段）。
- allow 角色反而 403/404 → 配置或会话问题（info）。

`authz_probe.py` 会输出每个角色的状态、最终 URL、标题、内容相似度与证据路径。

## 数字 ID 的技巧

- 先确认路由是否只取前导数字：`/orders/123'` 仍返回 123 → 路由层解析，不是 SQLi。
- 取真实归属：用 SQLi/报表/管理端找出对象属于哪个 tenant，再让另一 tenant 访问。
- 跨租户返回 404 不代表没洞：可能是“按归属隐藏”；换 ID 范围、换对象类型再试。

## 证据

- 角色 A 的请求 + 200 响应；
- 角色 B 的同一请求 + 403/404（对照）；
- 对象归属证明（订单号、商户名、用户 ID）；
- 原始响应路径。

## 修复

服务端按“对象归属 + 角色 + 动作”授权；不要只隐藏前端入口；对批量赋值使用字段白名单；对导出/报表同样加 tenant 过滤。
