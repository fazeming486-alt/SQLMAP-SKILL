# 业务逻辑与竞争条件 playbook

## 适用面

退款审批、优惠券/积分、库存扣减、结算、邀请奖励、审批流、配额与限次。共同点：**先查后写**、状态机、金额/数量可被并发或重放影响。

## 观测点

| 对象 | 看什么 |
|---|---|
| 状态机 | 同一单据能否从终态再次流转；跳过中间态 |
| 幂等 | 同一请求重复提交是否重复入账/发货 |
| 账本 | 双分录是否平衡；余额/额度是否多增少减 |
| 配额 | 每租户/每用户的上限能否并发突破 |
| 时间 | 过期券、跨期结算、时区与边界值 |

## 竞争测试设计

1. 选**可逆、低风险**的动作（靶场内退款/领券），绝不压测生产。
2. 低并发起步：2 → 5 → 10 个请求，同一会话与 CSRF，尽量同一时刻发出（线程 barrier）。
3. 每个请求记录：响应码、结果文案、耗时；结束后查最终状态与账本。
4. 判据：
   - 多次成功 / 重复入账 / 余额多增 = 竞争成立（高危）。
   - 1 次成功、其余“已处理/已审批” = 状态检查或唯一索引生效，记为**防御通过**。
   - 全部 5xx/429 = 观测无效，降并发/冷却后再试。
5. 证据：并发脚本、时间线、响应摘要、最终账本截图；不要只贴“成功一次”。

## 常见根因与修复

- 应用层“先 SELECT 再 UPDATE”：改原子更新（`UPDATE ... WHERE status='pending'`）并检查影响行数。
- 无幂等键：请求带 `Idempotency-Key`，服务端唯一索引落库。
- 无唯一约束：账本/明细加业务唯一索引，事务内写双分录。
- 隔离级别不足：涉及金额的读改写加行锁或串行化。
- 限次用缓存计数：用原子自增/数据库约束，不用“读-加一-写”。

## 报告写法

时间线 + 并发数 + 每请求结果 + 最终状态；若未复现，明确写“已测试的并发与判据，未突破”，避免把无效观测写成漏洞。

## 注意

- 仅限授权靶场/自有环境；禁止对第三方或生产做并发压测。
- 退款/结算类动作优先在可重置的种子数据上做；结束后用种子脚本恢复。
